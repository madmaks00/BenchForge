# BenchForge — прототип на C# / .NET 10 / Avalonia

Настольное приложение для сравнения баз данных с отдельным C#-процессом генератора нагрузки. Это новая версия проекта; Python для её запуска не нужен.

Реализован **один движок — C#/.NET**. Java, Python, Rust, Node.js и Go перечислены как запланированные реализации общего протокола, их кода здесь пока нет. Node.js обозначает будущую среду выполнения JavaScript.

Новый эксперимент создаётся по шагам. Прогресс и журнал доступны в «Выполнении». В «Отчётах» находятся история запусков и импорт `report.json`. [Как читать результаты](docs/reading-results.md).

В разделе **Нагрузка → Окружение тестирования** доступен запуск каждой базы и повтора в чистой Linux-VM из выключенного шаблона. Для него нужен Multipass 1.15 или новее. [Подготовка и запуск виртуальных машин](docs/virtual-machines.md).

## Запуск

Для сборки из исходников нужен **.NET 10 SDK**. Первый запуск из исходников требует интернета для восстановления NuGet-пакетов. Готовой Windows-сборке достаточно .NET 10 Runtime: распакуйте её целиком и откройте `BenchForge.Desktop.exe`. Для серверных СУБД нужен работающий Docker с Linux containers. SQLite запускается без Docker.

**Windows:** распакуйте исходники целиком и откройте `start.cmd`.

**macOS / Linux:** откройте терминал в папке проекта и выполните `bash start.sh`.

Для первого теста оставьте выбранную SQLite и профиль **«Быстрая проверка»**. Пройдите шаги **«Нагрузка»** и **«Проверка»**, затем нажмите **«Запустить эксперимент»**. Для серверного теста выберите нужные базы. При первом использовании каждой серверной базы загружается её Docker-образ.

## Профили нагрузки

| Профиль | Что задаётся |
| --- | --- |
| Быстрая проверка | Короткий прогон для проверки запуска и запроса |
| Постоянная нагрузка | Число клиентов и длительность |
| Рост нагрузки | Начало, потолок, число ступеней и длительность ступени |
| Пиковая нагрузка | Клиенты до пика и на пике, время до пика, на пике и после |
| Длительный тест | Постоянное число клиентов, общая длительность и интервалы измерения |
| Заданная частота | Операции в секунду, предел параллельности и время |
| Свой график | Точки времени, число клиентов, частота и кривая между точками |

[Описание режимов, графика и всех настроек нагрузки](docs/load-profiles.md).

Постоянная нагрузка, рост и пик адаптированы из [API-Load-Orchestrator](https://github.com/madmaks00/API-Load-Orchestrator/blob/d11ad7ae0cec1a88733150987d8eabeb4488c6da/src/hooks/useLoadEngine.ts). Рост в BenchForge идёт ступенями с измерением на каждом уровне. Ступени и интервалы выполняются последовательно на одном подготовленном наборе. Между ними завершаются запросы предыдущего этапа, при необходимости открываются подключения и проверяется целостность данных.

В отчёте **«Сравнение»** сопоставляет базы на выбранном этапе, а **«Ход нагрузки»** показывает последовательность этапов, скорость, p99, ошибки и память. Для заданной частоты доступны доля пропусков и p99 с ожиданием запланированного старта. Планы нагрузки, сохранённые в JSON, можно повторить командой `--config`. Конфигурации со списком `clients` по-прежнему поддерживают отдельные запуски на каждом уровне.

Для редактирования откройте **BenchForge.slnx** в поддерживающей .NET 10 версии Visual Studio или Rider, либо **BenchForge.code-workspace** в VS Code.

```sh
dotnet build BenchForge.slnx -c Release
dotnet test tests/BenchForge.Tests/BenchForge.Tests.csproj -c Release
dotnet run --project src/BenchForge.Cli -c Release -- --smoke
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/all-databases.json
```

Командный режим поддерживает `--targets`, `--engines`, `--check --config FILE`, `--reports DIRECTORY`. Ctrl+C включает остановку с сохранением отчёта.

## Базы и профили

| СУБД | Профиль первой версии |
| --- | --- |
| PostgreSQL | Чтение по ID, диапазон до 100 записей, агрегация по группе, атомарные обновления, смешанная нагрузка, вставка, батчи, удаление |
| MySQL | Те же операции через MySqlConnector; отдельный экземпляр от MariaDB |
| MariaDB | Те же операции через MySqlConnector; своя версия и настройки в отчёте |
| MongoDB | CRUD, диапазоны, агрегация и батчи; один узел, `w=1,j=true`, автоматические повторы записи выключены |
| Redis | Hash на запись; HGETALL, HINCRBY, HSET, DEL, конвейерная запись пакетов; режим кеша в памяти |
| Valkey | Отдельный сервер с тем же профилем ключей; не объединяется с Redis в одну строку |
| ClickHouse | MergeTree, диапазоны, агрегация, аналитическое сканирование и пакетные вставки через HTTP / JSONEachRow |
| SQLite | Встраиваемая база, WAL и `synchronous=FULL`; нет сети и отдельного серверного процесса |

Пакетные транспорты различаются и фиксируются в отчёте: PostgreSQL — binary COPY; MySQL/MariaDB — параметризованный multi-row INSERT; MongoDB — InsertMany; Redis/Valkey — конвейер HSET; SQLite — подготовленный INSERT внутри транзакции; ClickHouse — HTTP / JSONEachRow. Для Redis пакет не является атомарной транзакцией.

SQLite измеряет всю связку приложения, драйвера, движка SQLite, кеша и файловой системы. Отсутствие сети не делает результат «чистым временем диска».

В Redis/Valkey отключены AOF/RDB; это профиль кеша, его задержки записи не означают те же гарантии сохранности, что у SQL. ClickHouse тестируется как аналитическое хранилище: универсального рейтинга победителей между этими категориями приложение не назначает.

## Что измеряется

- Успешные операции/сек., для пакетных вставок также записи/сек.
- Средняя задержка, p50, p95, p99, максимум, отдельное распределение ошибок.
- Время от фактического начала запроса и, в режиме заданной частоты, от запланированного начала до ответа.
- Ошибки, пропущенные по расписанию запросы, число запланированных и завершённых операций.
- CPU и RSS/рабочий набор **процесса движка**, выделенные .NET байты, сборки поколений 0/1/2 и суммарная длительность пауз GC.
- CPU, RAM и выборочные разности счётчиков дискового ввода-вывода **контейнера базы**.
- Скорость первоначальной загрузки, отдельно время генерации данных, время индекса и статистики SQL.
- Фактические версии драйверов/СУБД, runtime, образ, режим GC и важные настройки записи/кеша.

Основные графики используют медиану повторов без ошибок, с пройденной проверкой и без отмены. Все исходные результаты сохраняются, в том числе ошибочные. Для пакетов единица графика — **записей/сек.**; для индекса — **секунды**; обычные операции — **операций/сек.**

## Две модели нагрузки

**Фиксированные клиенты (closed loop):** каждый клиент начинает следующий запрос после ответа на предыдущий.

**Заданная частота (constant rate):** запросам назначаются моменты старта, доступно не больше выбранного числа одновременно выполняющихся клиентов. Опоздавшие сверх `maxStartLagMs` слоты пропускаются и учитываются в `dropped`; бесконечная очередь не создаётся. В отчёте есть фактическая скорость и обе задержки — service и end-to-end.

Планировщик первой версии использует таймеры .NET с ожиданием около 1 мс. Точность зависит от ОС, нагрузки и числа клиентов; высокая заданная частота не гарантирует такую же фактическую выдачу. Пропуски и задержки старта позволяют обнаружить это ограничение. Пакет считается одной запланированной операцией, дополнительно учитывается число записей.

## Условия эксперимента

Каждое сочетание **СУБД × объём × клиенты × повтор** получает свежий временный экземпляр базы и новый процесс C#-движка. Запуски идут последовательно; порядок СУБД меняется между повторами. Первоначальная загрузка, прогрев, подготовка подключений и проверка данных исключаются из измеряемой фазы запросов.

Тесты выполняются с тёплым кешем: первоначальная проверка читает набор данных, затем выполняется выбранный прогрев. Кеши ОС и СУБД принудительно не очищаются.

После загрузки проверяются количество записей, сумма ID и сумма значений. После сценариев проверяется количество записей с учётом успешных вставок и удалений. Неопределённый исход записи может привести к расхождению — это ошибка проверки, а не успешный результат.

Данные генерируются пакетами с расчётным пределом полей около 8 МБ, без хранения всего набора в RAM. Алгоритм SplitMix64, алфавит и преобразования зафиксированы в [контракте движка](docs/protocol-v1.md). Максимум настройки набора — 100 млн записей; фактическая вместимость определяется ресурсами. Большие профили могут работать много часов.

Число клиентов — **логическая параллельность**, а не универсальное число TCP-соединений. SQL использует выделенное соединение на клиента, MongoDB — общий пул, Redis/Valkey — общий мультиплексор, ClickHouse — HTTP-пул. Эти различия записываются в метаданные. Разные языки в будущем будут сравниваться вместе с конкретными драйверами и runtime.

Лимиты CPU/RAM относятся к серверному контейнеру. SQLite работает внутри процесса движка и таких лимитов контейнера не получает. CPU/RAM интерфейса и координатора не подменяют метрики движка. Отдельные процессы на одном компьютере всё ещё конкурируют за общие ресурсы; для предельных испытаний следующий этап — удалённый агент и выделенный генератор.

## Метрики ресурсов и точность

Память процесса измеряется примерно раз в 250 мс, Docker — с его частотой выдачи (обычно около 1–2 секунд). Максимум означает максимум среди выборок, не гарантированный мгновенный пик. На коротком этапе выборки может не быть: значение остаётся пустым. Docker CLI на Linux исключает неактивный файловый кеш из RAM. CPU 100% соответствует одному логическому ядру и может быть выше 100%.

Окно серверных выборок привязано к получению управляющих событий координатором, поэтому границы приближённые. Дисковые показатели — разности выборочных счётчиков блочного ввода-вывода; это не размер БД и не точные IOPS.

Гистограмма `binary128-us-v1` имеет целые микросекунды, 128 корзин на каждый двоичный диапазон, ширину корзины до 0.782%. Значения ниже 1 мкс округляются вверх; переполнение диапазона около 71 минуты учитывается отдельно. Перцентили считаются из распределения; p99 разных потоков не усредняются.

Измеряемая service-задержка включает вызов драйвера, сериализацию запроса драйвером, сеть/выполнение и получение результата. Создание объектов новых записей выполняется перед service-таймером, но входит в фактическую пропускную способность и end-to-end задержку режима заданной частоты. Время загрузки включает генерацию, упаковку и запись; `generationSeconds` отдельно показывает генерацию объектов.

## Отчёты, остановка и очистка

В `reports/<UTC-время>-<ID>/` сохраняются `report.json`, `results.csv`, `summary.json` и исходные `resources-<caseId>.json`. CSV содержит в том числе ошибки, пропуски, GC и раздельные ресурсы. Времена и имя папки используют UTC. JSON отчёта заменяется атомарно после каждого этапа.

Остановка запрещает новые операции и ждёт завершения уже начатых. Обычные запросы ограничены таймаутами драйверов/сервера; подготовка индекса и большие пакеты загрузки могут занимать дольше. Если движок не завершается после отмены за 60 секунд, координатор завершает только запущенный им процесс. При аварии частичный отчёт остаётся.

Приложение не принимает адрес существующей рабочей БД через интерфейс: оно создаёт свои экземпляры с портами на `127.0.0.1`. Пароли передаются дочернему процессу через stdin и не сохраняются в отчётах. Контейнер удаляется только при совпадении метки текущего caseId, вместе с его анонимными томами. Скачанные образы остаются. При аварийном закрытии контейнер с именем `dblab-*` может остаться; ID и ошибки очистки видны в отчёте.

Подробное объяснение проектов и файлов: [Структура BenchForge](docs/structure.md).

## Статус

Это рабочий прототип, а не завершённый промышленный бенчмарк. Проверки и их фактические ограничения перечислены в [VALIDATION.md](VALIDATION.md). Прогоны на маленьких наборах подтверждают работу функций; они не доказывают точность и масштабируемость при миллионах запросов/сек.

Остаются для следующих этапов: другие языки, удалённые агенты, многомашинная генерация, сценарии транзакций/репликации/отказов, сравнение с эталонными специализированными инструментами, расширенная проверка больших данных и контроль нагрузки на выделенном оборудовании. Работа macOS/Linux требует сборки и испытания на соответствующих машинах; текущие проверки выполняются на Windows x64.

Первичные справочники: [.NET Worker](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers), [Avalonia](https://docs.avaloniaui.net/docs/supported-platforms), [Npgsql](https://www.npgsql.org/doc/basic-usage.html), [MySqlConnector](https://mysqlconnector.net/), [MongoDB.Driver](https://www.mongodb.com/docs/drivers/csharp/current/), [StackExchange.Redis](https://redis.io/docs/latest/develop/clients/dotnet/), [ClickHouse HTTP](https://clickhouse.com/docs/interfaces/http), [Microsoft.Data.Sqlite](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/).
