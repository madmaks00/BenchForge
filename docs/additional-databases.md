# DuckDB, Oracle, CockroachDB, Elasticsearch и OpenSearch

В BenchForge доступны 14 СУБД. Пять новых адаптеров, как и SQL Server, пока выполняются движком **C#**. При их выборе остальные языки отключаются; неподдерживаемая конфигурация из файла отклоняется до запуска.

| База | Для чего проверять | Стандартные операции | Свои SQL-сценарии |
| --- | --- | --- | --- |
| DuckDB | Встраиваемая аналитика, сканирование, агрегаты, пакетная загрузка | Чтение, диапазон, агрегация, аналитический диапазон, обновление, смесь, вставки и удаление | Да |
| Oracle Free | Реляционные запросы и транзакции в редакции Free | Все стандартные OLTP-операции | Да |
| CockroachDB | SQL и транзакции одного узла | Все стандартные OLTP-операции | Да |
| Elasticsearch | Документы, индексы и полнотекстовый поиск | Чтение по ID, диапазон, агрегация, обновление, смесь, вставки, удаление и полнотекстовый поиск | Нет; собственного редактора JSON-запросов пока нет |
| OpenSearch | Документы, индексы и полнотекстовый поиск | Тот же набор поисковых операций | Нет; собственного редактора JSON-запросов пока нет |

## Как запустить

Выберите базы, затем настройте тип нагрузки и операции. **Полнотекстовый поиск** доступен для Elasticsearch/OpenSearch; **Аналитический диапазон** — для DuckDB/ClickHouse. Можно выбрать все доступные операции: неподходящие для базы будут отмечены как неподдерживаемые. Полнотекстовый поиск выполняется перед удалением исходных записей.

SQLite и DuckDB работают без Docker. Остальным нужен Docker с Linux-контейнерами на выбранном ПК, внутри чистой VM или на Linux-сервере, которым приложение управляет по SSH. Для Oracle задайте минимум 2560 МБ RAM, для поисковых контейнеров — 2048 МБ, для CockroachDB — 1024 МБ. Память VM должна дополнительно покрывать систему и генератор; для Oracle используйте VM хотя бы с 4 ГБ. На первом запуске Oracle распаковывает данные: приложение ждёт его проверки готовности до 10 минут.

Пример всех новых баз находится в `configs/more-databases-smoke.json`:

```powershell
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/more-databases-smoke.json
```

По умолчанию используются образы Oracle `container-registry.oracle.com/database/free:latest-lite`, CockroachDB `cockroachdb/cockroach:v26.2.0`, Elasticsearch `docker.elastic.co/elasticsearch/elasticsearch:9.5.6`, OpenSearch `opensearchproject/opensearch:3.9.0`. Образы можно менять через `imageOverrides`; реальный ID образа и версия сервера записываются в отчёт. Тег Oracle `latest-lite` изменяется со временем.

На каждый прогон создаётся отдельный файл или контейнер. Файлы DuckDB и его WAL удаляются после закрытия движка; контейнеры и созданные для них анонимные тома удаляются после получения результатов. Существующие пользовательские базы не подключаются.

## Условия сравнения

**DuckDB** работает внутри процесса генератора. Настройки RAM и CPU задают бюджет менеджера памяти DuckDB и количество потоков запросов; они не ограничивают всю память процесса и не являются квотой CPU операционной системы. RAM базы отдельно от RAM генератора здесь измерить нельзя. Стандартные пакеты записываются через нативный appender внутри транзакции. В пользовательских сценариях используется общий SQL-загрузчик. Конфликты параллельных транзакций видны как ошибки, автоматического повтора нет.

**Oracle Free** запускается в редакции Free с её внутренними ограничениями. Для теста создаётся отдельный пользователь `DBLAB` внутри `FREEPDB1`, а не используются системные таблицы. Стандартная пакетная загрузка использует ODP.NET array binding внутри транзакции. Свой SQL работает через параметры, с BindByName. Автоматические имена таблиц и столбцов приводятся к верхнему регистру Oracle. Текст хранится в CLOB, текстовые ключи — NVARCHAR2(450), Guid — RAW(16), даты — TIMESTAMP(6). Общий маркер `@имя` преобразуется в `:имя` вне строк и комментариев. Для ограничения выдачи задавайте вариант Oracle с `FETCH FIRST ... ROWS ONLY`, как в шаблоне магазина. Скрипт схемы/индексов может содержать отдельные SQL-команды или один полный PL/SQL-блок. Допустимы ReadCommitted и Serializable; RepeatableRead не поддерживается.

**CockroachDB** запускается через `start-single-node`: один узел, без репликации, кворама и отказоустойчивости. Он не измеряет производительность распределённого кластера. Используется Npgsql и отдельная база `dblab`; стандартные пакеты — multi-row INSERT. По умолчанию база использует SERIALIZABLE, и конфликт может потребовать повтора транзакции. BenchForge такой повтор не скрывает: он учитывается как ошибка. Это нужно учитывать при сравнении с SQL-базами, у которых другой уровень изоляции по умолчанию.

**Elasticsearch/OpenSearch** используют один основной шард и ноль реплик. Текстовое поле детерминированно составлено из `benchforge groupN` и исходного payload, разбитого на слова по 16 символов. Так длинная случайная строка не пропускается стандартным анализатором как один слишком длинный токен. Запрос ищет первый термин исходной записи через стандартный анализатор и получает до 10 документов; генерация термина входит во время вызова. Документы и исходный текст проверяются при чтении. Это проверка выполнения и задержек поиска, а не качества релевантности.

При загрузке поисковый refresh отключён, во время запросов установлен интервал 1 с. Чтение по ID использует realtime GET; поиск использует обновляемый индекс. Подтверждение записи и видимость записи в поиске — разные события. Для контрольных сумм и числа документов выполняется явный refresh вне времени запросов. Каждая строка ответа bulk проверяется отдельно: HTTP 200 не считается гарантией успеха всех документов, пакет не является атомарной транзакцией. Translog использует долговечность `request`.

Поисковые контейнеры используют NIO (`node.store.allow_mmap=false`), чтобы не менять настройки ядра хоста. Половина RAM контейнера выделяется JVM heap. Авторизация выключена только для этих временных тестовых контейнеров; опубликован только loopback-порт тестового хоста. Результаты такого профиля нельзя автоматически переносить на кластер с TLS, репликами и другими настройками хранения. В удалённом режиме управление и отчёты передаются по SSH.

В отчётах эти категории помечаются разными профилями. Сравнивайте одинаковые операции и учитывайте транспорт, изоляцию, редакцию, репликацию, видимость записей и лимиты. Одно число не выбирает победителя для всех задач.
