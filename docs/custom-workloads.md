# Свои структуры, данные и SQL-нагрузка

BenchForge умеет выполнять пользовательский SQL-сценарий движком **C#** с **PostgreSQL, MySQL, MariaDB, SQLite, SQL Server, DuckDB, Oracle и CockroachDB**. Сценарий описывает таблицы, исходные данные, бизнес-операции и проверки. Он работает локально, в чистой VM и на Linux-сервере под управлением по SSH. Остальные языки и NoSQL-базы доступны в стандартных тестах.

## Быстрый старт в приложении

1. Выберите базы, перейдите к **Нагрузке** и в поле **Что тестируем** выберите **Свои таблицы и SQL-запросы**.
2. Откройте редактор. Можно начать с магазина, кошельков или пустого примера.
3. На вкладке **Таблицы и данные** добавьте таблицы и поля, выберите типы и генераторы либо импортируйте CSV/JSONL.
4. На вкладке **Операции** опишите запросы, их параметры, ожидаемые ответы и шаги транзакций.
5. Проверьте схему, индексы и контрольные запросы. Кнопка **Пробный запуск SQLite** действительно создаёт временную SQLite, загружает данные и выполняет запросы. Это проверка SQLite-варианта сценария; она не проверяет синтаксис других СУБД.
6. Примените сценарий. Задайте график нагрузки, базовый объём и повторы в главном окне, выберите окружение и запустите эксперимент.

Проба использует 100 базовых строк и короткие окна. Фиксированные наборы и импортированные файлы загружаются целиком. Для больших файлов это тоже может быть долгой операцией; пробу можно остановить.

## Таблицы и объёмы

Для каждой таблицы доступны:

- **Имя** — латинские буквы, цифры и подчёркивания, до 63 символов; удобнее использовать нижний регистр.
- **Поля** — имя, тип, генератор, NULL, первичный и уникальный ключи.
- **Множитель** — число строк равно базовому объёму, умноженному на это значение.
- **Фиксированное число строк** — заменяет формулу. Значение 0 создаёт пустую таблицу.
- **Импорт** — заменяет генерацию и загружает весь файл при каждом прогоне, независимо от базового объёма.

Например, при базовом объёме 1000 шаблон магазина создаёт 1000 покупателей, 100 товаров, 2000 заказов и 4000 позиций: всего 7100 строк. В отчёте базовый объём остаётся осью эксперимента, а реальные размеры таблиц доступны в описании сценария.

Таблицы загружаются сверху вниз. `Reference` выбирает существующий числовой ключ из предыдущей таблицы. Для него нужны первичные ключи **1..N без пропусков**. Это проверяется и для импортированных родительских таблиц. Другую систему ключей можно использовать со своими параметрами и SQL, без `Reference`.

Автоматическая схема создаёт типы полей, первичные/уникальные ключи и внешние ключи для `Reference`. Доступны Int64, Int32, Decimal, Double, Text, Boolean, DateTime и Guid. Для составных ключей, особых типов и ограничений задайте собственный SQL схемы. Все загружаемые таблицы должны быть перечислены в сценарии. Схемы с произвольными дополнительными объектами требуют SQL, который корректно обрабатывает повторную подготовку этих объектов.

## Генераторы значений

| Генератор | Поведение |
| --- | --- |
| Sequence | Последовательность от `min`: при загрузке по номеру строки, в параметрах — по глобальному номеру попытки операции |
| Integer | Равномерное целое между `min` и `max`, включая границы |
| Decimal | Случайное число в диапазоне с заданным числом знаков после запятой |
| Text | Префикс и заданное число случайных ASCII-символов |
| Choice | Выбор значения из списка; повторение значения увеличивает его вероятность |
| Reference | Числовой ключ из исходного размера указанной таблицы |
| Sample | Реальное ненулевое значение указанного столбца из входных данных, в том числе строка или UUID |
| Guid | Детерминированный идентификатор для тестовых данных |
| Timestamp | UTC-дата из диапазона Unix-секунд |
| Boolean | Случайное логическое значение |
| Constant | Постоянное значение; NULL при отсутствии значения |
| Key | Ключ текущей операции из базового диапазона |
| Client | Номер клиентской сессии |

Префикс Text понимает `{row}`, `{sequence}`, `{key}`, `{client}`. Например, `user-{row}@example.test` и длина случайной части 0 дают повторяемые адреса. Случайные GUID здесь предназначены для данных теста.

Для nullable-полей можно задать вероятность NULL. Один seed, порядок полей и описание сценария воспроизводят исходные генерируемые данные. Параллельное выполнение запросов и итоговое состояние изменяемых данных не обязаны воспроизводиться в том же порядке.

Sample предназначен для параметров запросов. Он собирает повторяемую reservoir-выборку во время загрузки исходных данных: по умолчанию до 10 000 ненулевых значений на столбец/настройку. Размер можно изменить; больший размер требует больше RAM генератора. Если исходных значений больше лимита, запросы работают с выборкой, что влияет на локальность обращений и кеш. При SQL-триггерах, преобразующих входные значения, учитывайте, что выбираются исходные значения, а не повторно прочитанные значения БД. Reference охватывает весь числовой диапазон 1..N без хранения ключей в памяти.

Глобальный флажок популярных ключей влияет на `@key`/Key. Reference самостоятельно выбирает ключи своей таблицы равномерно. Размер обычного поля payload не управляет своими таблицами: длины задаются в редакторе полей.

## CSV и JSONL

CSV должен содержать заголовок. При импорте определяются разделители **запятая, точка с запятой или табуляция**; поддерживаются кавычки, экранированные кавычки, переносы внутри поля, UTF-8 и BOM. Десятичные значения внутри полей задаются с точкой.

JSONL — один объект JSON на строку. Имена его полей соответствуют столбцам таблицы. Вложенный объект можно хранить как текст; автоматического создания связанных таблиц из вложенного JSON нет.

Импорт определяет предварительные типы по первым 1000 записям; проверьте их вручную. Название `id` с целочисленным типом предлагается как первичный ключ. Пустое nullable-поле CSV становится NULL; JSON `null` тоже становится NULL. В обязательном поле отсутствие значения вызывает ошибку. Типы всех строк проверяются при загрузке в БД.

Приложение хранит рабочую копию импортированных данных. Для больших файлов на вкладке настроек редактора можно заранее выбрать диск/папку. По умолчанию используется каталог данных приложения `BenchForge/workloads`. Исходный файл не изменяется. В описании хранятся имя файла, формат, число строк и SHA-256; изменение байтов файла требует повторного импорта или обновления описания.

В отчёт не вкладываются записи CSV/JSONL. При выбранном Linux-сервере входные файлы передаются на этот сервер; после завершения и успешного получения отчёта их временная серверная копия удаляется. При потере связи файлы остаются там до завершения получения/очистки задания. В VM они удаляются вместе с VM.

## Операции, параметры и SQL

Операция имеет уникальный ID, название, вес и один или несколько SQL-шагов. Вся операция считается **одной операцией в секунду**, даже если она содержит пять SQL-команд. Её задержка включает пользовательские параметры, все шаги, чтение ответа, проверки шага и фиксацию транзакции.

Значения передаются параметрами `@имя`, без подстановки текста в SQL. Пользовательские параметры генерируются один раз на всю операцию и повторно используются её шагами.

Встроенные параметры:

| Параметр | Значение |
| --- | --- |
| `@key` | Ключ 1..базовый объём, с учётом настройки популярных ключей |
| `@sequence` | Уникальный номер попытки после базового объёма; не обещает отсутствие пропусков |
| `@client` | Номер клиентской сессии |
| `@baseRows` | Базовый объём данного прогона |
| `@seed` | Seed как знаковое 64-битное значение |
| `@rows_таблица` | Исходный размер таблицы, включая полный размер импортированного файла |

`@sequence` не учитывает множитель конкретной таблицы. Для вставки после исходных строк используйте, например, `@rows_orders + @sequence`. Генератор параметров Sequence начинается со своего `min` и не равен встроенному `@sequence`.

Шаги поддерживают:

- **Rows** — полностью прочитать результат, проверить минимум/максимум строк.
- **NonQuery** — выполнить запись и проверить число затронутых строк.
- **Scalar** — получить первое значение, при необходимости сравнить его текстовое представление с ожидаемым.
- **CaptureAs** — сохранить Scalar в именованный параметр для следующих шагов. Например, первый шаг получает ID, второй использует `@chosen_id`.

Флажок транзакции объединяет шаги: ошибка SQL или ожидания вызывает откат. Доступны Default, ReadCommitted, RepeatableRead и Serializable; для SQLite выбирайте Default или Serializable. Параметры команд и подключения подготавливаются вне измеряемого окна. Подготовку SQL можно отключить. Таймаут задаётся на одну команду, а не на всю многошаговую операцию.

Операции, отмеченные как разрешённые для прогрева чтением, используются перед измерениями. Флажок задаёт намерение автора сценария: автоматически доказать отсутствие записи в произвольном SQL приложение не пытается. Операции записи следует исключать из прогрева.

## Смесь, отдельные замеры и состояние

- **Смесь запросов / Mix:** на каждую попытку выбирается операция с вероятностью `вес / сумма весов`. Например, 50/40/10 дают ожидаемые доли 50%, 40%, 10%. В коротком прогоне фактические доли отличаются.
- **Каждая операция отдельно / Separate:** полный график выполняется для каждого включённого действия.
- **Отдельно и затем смесь / SeparateAndMix:** оба варианта последовательно.

По умолчанию таблицы заново создаются и загружаются перед отдельной операцией и перед смесью. Эту настройку можно отключить для продолжения работы с накопленным состоянием. **Интервалы одного графика всегда используют общее состояние**, как и в стандартных тестах. График повторяется для каждой единицы выполнения, а не распределяется между ними.

Все стандартные профили нагрузки, свои точки графика, повторы, лимиты контейнеров и модель заданной частоты сохраняются. В заданной частоте целевое число относится к бизнес-операциям. Пропуски относятся ко всей смеси; приложение не приписывает их конкретным действиям.

## Проверки целостности

Контрольный запрос возвращает число. Его можно сравнить с ожидаемым через Equal, AtLeast или AtMost. Ожидание — число, `baseRows` или `rows:имя_таблицы`. Перед нагрузкой и после каждого измеренного интервала проверки выполняются вне времени запросов. Ошибка делает текущий интервал непроверенным и останавливает этот прогон.

В контрольном SQL доступны `@completed` — накопленное число успешных операций после последней загрузки — и `@completed_IDоперации`, а также размеры таблиц. Например, можно проверять исходный размер плюс число успешно созданных заказов. Попытки прогрева в эти счётчики не входят.

Шаблон кошельков проверяет `SUM(balance) - COUNT(*) * 10000 = 0`. Такой контроль обнаруживает неполные переводы, даже если отдельные команды не сообщили об ошибке.

## Пакет, JSON и отчёты

**Сохранить пакет** создаёт `.bfworkload`: описание `workload.json` и необходимые входные файлы. Его можно перенести на другой компьютер и открыть в приложении. При открытии проверяются состав архива и контрольные суммы. Пакет с импортом содержит сами данные — учитывайте это при передаче.

Обычный JSON-сценарий тоже поддерживается: относительные пути файлов считаются от его папки. Полное описание доступно на вкладке JSON редактора с явными кнопками обновления и применения. **Сохранить настройки** сохраняет весь эксперимент и копирует входные файлы рядом; отличающийся существующий файл не перезаписывается.

В отчётах доступны:

- Графики и таблицы отдельных операций и смеси.
- Разбор смеси: успешные действия, ошибки и p99 по каждому ID операции.
- `operations.csv` — подробные действия для Excel, отдельно от общего `results.csv`.
- `report.json` — описание сценария, SHA-256, исходные размеры, результаты и гистограммы по действиям.

В счётчике обработанных строк суммируются возвращённые/затронутые строки всех шагов. RAM/CPU измеряются для всего генератора и контейнера БД; они не распределяются между действиями смеси. Процентили по действиям считаются из их собственных гистограмм.

Подготовка и загрузка имеют отдельные имена этапов. Для времени схемы/индексов меньше секунд означает быстрее; для загрузки больше строк/с означает быстрее. Ошибочные, отменённые и непроверенные измерения исключаются из скоростной сводки.

## Командная строка

Из корня исходников:

```sh
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/custom-sql-smoke.json --workload configs/workloads/store.json
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/custom-sql-smoke.json --workload configs/workloads/wallets.json
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/custom-sql-smoke.json --workload configs/workloads/imported-products.json
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/custom-sql-smoke.json --workload scenario.bfworkload
```

Для сервера используйте настройки `remoteServer` в обычном файле эксперимента и тот же `--workload`. На сервер один раз передаётся архив входных файлов; приватный SSH-ключ остаётся на управляющем ПК. После обновления исходников подготовьте серверный агент заново.

В конфигурацию эксперимента также можно вложить объект `customWorkload` целиком. Аргумент `--workload-inputs DIRECTORY` задаёт корень входных файлов; его используют агенты VM/SSH. В обычном запуске достаточно положить файлы рядом с JSON по указанным относительным путям.

## Границы текущей версии

Здесь сравниваются свои SQL-сценарии на четырёх SQL-СУБД через C#. Структуры MongoDB, Redis/Valkey и ClickHouse требуют других адаптеров пользовательских сценариев. Стандартные тесты этих баз и остальных языков продолжают работать.

Миллионы строк, реальные длительные нагрузки и предельная параллельность требуют отдельной проверки на вашем сервере. Короткая успешная проба подтверждает работу сценария и проверок, но не доказывает пригодность конфигурации для промышленной нагрузки. Корректность бизнес-условий зависит от проверок, которые задаёт автор сценария.

SQL Server использует отдельные варианты SQL (`overrides.sqlServer`), например TOP вместо LIMIT. [Профиль, типы данных и условия](sql-server.md).

Oracle и DuckDB используют адаптацию параметров и собственные SQL-диалекты. Elasticsearch/OpenSearch не выполняют пользовательский SQL. [Условия новых адаптеров](additional-databases.md).
