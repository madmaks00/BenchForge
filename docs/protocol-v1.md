# Протокол движка BenchForge v1

Первая реализация — C#. Контракт не требует .NET для будущих Java, Python, Rust, Node.js и Go workers.

## Процесс и сообщения

Worker — самостоятельный процесс. stdin/stdout содержат JSON Lines в UTF-8; stdout предназначен только для протокола. Пароли идут в приватном stdin, не в командной строке. Отдельная программа-драйвер отправляет запросы напрямую в СУБД; UI не находится в пути каждого запроса.

После старта worker отправляет `hello`: engine, runtime, версии алгоритмов и доступные сценарии. Координатор отправляет:

```json
{
  "protocolVersion": 1,
  "type": "run",
  "run": {
    "runId": "case-identifier",
    "target": "sqlite",
    "rows": 1000,
    "clients": 2,
    "repeat": 1,
    "config": {
      "targets": ["sqlite"],
      "datasetRows": [1000],
      "clients": [2],
      "durationSeconds": 5,
      "warmupSeconds": 1,
      "repeats": 1
    },
    "endpoint": {
      "host": "", "port": 0, "username": "", "password": "", "database": "",
      "filePath": "/temporary-owned-path/test.sqlite3"
    }
  }
}
```

Для серверов endpoint содержит только адрес созданного координатором временного экземпляра. Он не переносится в отчёт. Все реальные сообщения формируются типами `BenchForge.Contracts`.

Ответы имеют `protocolVersion`, `type`, `runId`, `data`:

- `metadata`: engine/runtime/driver/serverVersion/settings;
- `log`: диагностическое сообщение;
- `phase_start`: phase/targetSeconds;
- `progress`: агрегированный прогресс, примерно раз в секунду;
- `unsupported`: неподдерживаемый сценарий, без фиктивного нулевого результата;
- `result`: PhaseResult со счётчиками, гистограммами и метриками клиента;
- `completed`: завершение и признак cancelled;
- `failed`: ошибка с удалённым из текста паролем.

Отмена: `{"protocolVersion":1,"type":"cancel"}`. Закрытие stdin также останавливает worker. Коды выхода: 0 — успех; 1 — ошибка; 2 — отмена. Потеря процесса без `completed` не считается успехом. Управляющие каналы только локальные; удалённого RPC в этой версии нет.

## Данные: splitmix64-ascii-v1

Все операции с ulong выполняются с переполнением по модулю 2^64. Next:

1. state += `0x9e3779b97f4a7c15`;
2. z = state;
3. z = (z XOR (z >> 30)) × `0xbf58476d1ce4e5b9`;
4. z = (z XOR (z >> 27)) × `0x94d049bb133111eb`;
5. вернуть z XOR (z >> 31).

Начальное состояние записи: seed XOR (id × `0xd6e8feb86659fd93`). Первый Next задаёт amountCents = Next % 1 000 000 + 1. Каждый следующий Next выбирает символ payload по индексу Next % 62 из `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`. GroupId = (id−1) % 100; Version = 0. ASCII-символ занимает один байт UTF-8.

Эталон Next для state=0: `e220a8397b1dcdaf`, `6e789e6aa1b965f4`, `06c45d188009454f`. Будущие workers должны пройти эти и расширенные тесты до включения в сравнение. Общего seed встроенных Random разных языков недостаточно.

## Гистограмма: binary128-us-v1

Длительности считаются монотонными часами worker и переводятся в микросекунды. Значение округляется вверх до целой микросекунды, минимум 1. Для u < 2^32: e=floor(log2(u)), offset=floor((u−2^e)×128/2^e), bucket=e×128+offset.

Результат передаёт разреженный словарь bucket→count, Count, SumMicroseconds, MaxMicroseconds и Overflow. Верхняя граница корзины: 2^e + ceil((offset+1)×2^e/128) − 1 микросекунд. Перцентиль использует ближайший ранг ceil(Count×q) и верхнюю границу соответствующей корзины. Среднее — SumMicroseconds/Count, а не среднее границ корзин. Значения >=2^32 мкс ограничиваются последней корзиной с увеличением Overflow.

Гистограммы service, end-to-end и ошибок передаются отдельно. Общий перцентиль вычисляется из сумм счётчиков корзин, не усреднением p99 отдельных клиентов. Точная сумма длительностей и максимум сохраняют исходную точность часов до округления корзины.

## Что сравнивает отчёт

Связку конкретных языка/runtime/драйвера/транспорта/СУБД/настроек. Для сравнения баз фиксируется движок; для сравнения движков — база, данные, сценарий, размещение и модель нагрузки. Другие реализации пока не подключены.
