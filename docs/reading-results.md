# Как читать результаты BenchForge

В Visual Studio выберите стартовым проектом **BenchForge.Desktop**, конфигурацию **Release** и запустите **Ctrl+F5**.
Откройте **«Отчёты»** и выберите сохранённый запуск в списке. Кнопка **«Импортировать отчёт»** открывает `report.json` из другой папки.

## Куда смотреть

1. **Сравнение** показывает график и вывод для выбранной операции. Переключайте операцию и показатель в левой панели. Скорость измеряется в операциях или записях за секунду. p99 измеряется в миллисекундах и описывает медленную часть ответов. Создание индекса измеряется в секундах. Разверните **«Все операции»**, чтобы увидеть результаты разных задач, или **«Показатели, условия и замечания»**, чтобы посмотреть настройки и окружение.
2. **Масштабирование** показывает скорость и p99 при изменении числа клиентов или объёма данных. Точки соответствуют измеренным уровням. Наведите на точку, чтобы увидеть значение.
3. **Измерения** показывает каждый отдельный повтор. Выберите строку для расшифровки. Флажок **«Ресурсы»** добавляет память, CPU, паузы сборщика мусора и запись на диск.
4. **Справку** можно открыть кнопкой **«?»** в шапке. Журнал текущего запуска находится в разделе **«Выполнение»**.

Фильтры объёма и клиентов относятся к открытому отчёту. Чтобы задать параметры для следующего теста, перейдите в **«Новый эксперимент»**.

## Пример из вашего отчёта PostgreSQL / MySQL

При чтении по ID, 1 000 записях и одном клиенте:

- PostgreSQL: около 1 246 успешных чтений/с.
- MySQL: около 1 169 успешных чтений/с.
- PostgreSQL показала на 6,6% больше чтений/с относительно MySQL в этом прогоне.

Это один повтор примерно по секунде. Он показывает наблюдавшуюся разницу; её устойчивость ещё неизвестна. По нему нельзя объявить одну СУБД лучшей для любых задач. При двух клиентах графики показывают рост скорости и изменение медленных ответов отдельно.

## Как оценивать ограничения

Медиана — центральное значение упорядоченных повторов; для двух средних берётся их среднее. На сравнении точками отмечены измерения, отрезком — минимум и максимум. При одном повторе разброс неизвестен.

Карточка рядом с графиком показывает итог базовых проверок:

- **Пробные измерения** — меньше трёх повторов с данными выбранного показателя или измерение запросов короче минуты. На подготовку данных порог длительности не распространяется.
- **Есть разброс** — диапазоны двух ведущих результатов пересекаются или разброс одной серии превышает 10% от медианы. Разброс считается как `(максимум − минимум) / медиана`. При нулевой медиане процент не рассчитывается.
- **Проверьте условия** — отличаются профили хранения, единицы или настройки этапа, сохранены разные версии/лимиты одной БД либо обнаружена сборка Debug.
- **Неполные данные** — эксперимент не завершён полностью, есть ошибки, отменённые прогоны, пропуски нагрузки или отсутствующие измерения.
- **Наблюдение по повторам** — перечисленные базовые проверки не выявили ограничений. Это не подтверждение статистической значимости или полной идентичности условий.

При ограничениях крупный заголовок объясняет проблему, а наблюдавшийся процент остаётся ниже с подписью **«По медианам»**. В **«Почему такой вывод»** доступны причины, рекомендации и диапазоны повторов. Для CPU/RAM и долей ошибок/пропусков заголовок описывает показатель, не выбирая лучшую базу по расходу ресурсов.

Пороги длительности, повторов и разброса — подсказки интерфейса, а не статистические тесты. Пересечение диапазонов само по себе не доказывает ни наличие, ни отсутствие значимой разницы. Для следующих сравнений увеличьте длительность и число повторов, проверяя разброс и одинаковые условия.

Счётчик повторов относится к выбранному показателю: три результата запросов с одной выборкой RAM дают один повтор с данными RAM. Отсутствующие метрики не превращаются в нули. Условия окружения показывают обычный запуск или чистую VM и её ресурсы.

Версии, образы, драйверы и лимиты проверяются по сохранённым метаданным для одной БД и одного движка во всём отчёте. Разные ID загрузки и имена VM ожидаемы и не считаются изменением условий. Для старых отчётов без подходящих метаданных выводится пояснение: приложение не восстанавливает неизвестные настройки задним числом. Проверки не подтверждают одинаковые гарантии сохранения данных у разных СУБД и не устраняют влияние общего физического железа.

Скорость и задержки в сводке используют проверенные прогоны без ошибок. Ошибочные результаты остаются в подробностях и в графике доли ошибок. Пропуски заданного расписания нужно оценивать вместе с фактической скоростью.

«Нет данных» означает отсутствие измерения или неподдерживаемую операцию, а не нулевое потребление. SQLite работает в процессе генератора, поэтому отдельной серверной RAM и CPU нет.

Меньшее потребление памяти само по себе не делает базу лучше: память используется и для кеша. RAM/CPU базы и генератора разделены. Ресурсы сервера измеряются выборками; очень короткий этап может остаться без выборки.

Результаты относятся к этому железу, окружению, данным, драйверу и настройкам. SQL, встроенная SQLite, Redis/Valkey и ClickHouse имеют разные профили работы и гарантии записи. Универсальный общий балл для них не рассчитывается.

## Проверка обновления

Проверки анализа покрывают короткие и неполные тесты, пересекающиеся и непересекающиеся диапазоны, большой разброс, отсутствующие метрики, разные профили хранения, изменения версий и лимитов, ожидаемые разные ID виртуальных машин и сборки Debug. Интерфейс проверяется отдельно на примерах коротких, нестабильных и стабильных повторов. Демонстрационные числа для UI не являются результатами испытания БД.
