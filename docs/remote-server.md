# Тестирование Linux-сервера

BenchForge на вашем компьютере управляет экспериментом по SSH. Генератор нагрузки, его драйверы и временные базы работают **на выбранном Linux-сервере**. На ПК поступают прогресс и готовые измерения. Скорость и задержки запросов измеряет серверный движок: время доставки прогресса по SSH к ним не прибавляется.

Это проверка базы вместе с генератором на одном сервере. Она не измеряет задержку сети между отдельным сервером приложения и сервером БД. Генератор, базы и системные процессы делят ресурсы сервера; абсолютной независимости от соседних процессов, частот CPU и кеша здесь нет.

## Что нужно

- Выделенный для испытаний Linux x64 или ARM64, SSH и обычный Docker Engine с сокетом `/var/run/docker.sock`. Rootless Docker и удалённый Docker context в этом режиме не поддерживаются.
- SSH-пользователь, который может запускать Docker без запроса пароля. Доступ к Docker даёт широкие права на сервере; используйте тестовую машину.
- Стандартные Linux-инструменты: `sh`, `flock`, `tar`, `sha256sum`, `tail` с поддержкой `--pid`, `stat`. Подходит Ubuntu 24.04.
- Достаточно памяти для генератора и выбранной базы, свободное место под Docker-образы, данные и отчёты. Интернет при подготовке нужен для образов и зависимостей.
- На управляющем ПК — клиент OpenSSH и настроенный вход по ключу. .NET, Java и другие языки устанавливать на сервер вручную не нужно: они попадают в образ агента.

Если Docker уже установлен, сначала проверьте из обычного терминала `ssh ubuntu@АДРЕС`, подтвердите правильный отпечаток сервера и выполните там `docker info`. Установка Docker и выдача прав пользователю остаются отдельной административной настройкой вашего сервера.

## Запуск из приложения

1. Выберите базы, перейдите к нагрузке и откройте **Окружение тестирования → Linux-сервер**.
2. Укажите адрес, SSH-пользователя и порт. Вместо адреса можно использовать алиас из локального SSH config. Поле пользователя можно оставить пустым для пользователя из SSH config; порт в интерфейсе задаётся явно.
3. При необходимости раскройте параметры SSH и укажите локальный файл ключа и `known_hosts`. Приватный ключ остаётся на ПК. Вход с интерактивным запросом пароля не поддерживается; можно использовать `ssh-agent`.
4. Выберите движки нагрузки и нажмите **Подготовить сервер**. BenchForge передаст исходники агента и соберёт Docker-образ с выбранными языками. При изменении исходников или набора языков подготовку нужно повторить.
5. Задайте операции, нагрузку и повторы. На шаге проверки убедитесь, что указано нужное имя сервера, и запустите эксперимент.

На этом ПК не требуется запущенный Docker или установленные дополнительные движки. Серверный агент создаёт собственные временные экземпляры СУБД. Подключение к существующей базе с рабочими данными в этой версии не предусмотрено.

## Потеря связи и остановка

Задание запускается в отдельном Docker-контейнере и продолжает работу при потере SSH-соединения. После нескольких неудачных подключений приложение покажет, что связь потеряна, и сохранит уже полученные результаты. Это **не означает остановку нагрузки**.

В настройках того же сервера нажмите **Продолжить наблюдение**. Приложение найдёт последнее незавершённое задание, перечитает его события и получит отчёт, не выполняя запросы повторно. Запись подключения хранится на ПК в каталоге приложения `BenchForge/remote-jobs`; в Windows это `%LOCALAPPDATA%\BenchForge\remote-jobs`.

Кнопка остановки отправляет серверу запрос отмены. Затем приложение ждёт сохранения частичного отчёта. Если отмену нельзя подтвердить, задание остаётся доступным для повторного подключения. При закрытии окна во время наблюдения приложение тоже запрашивает остановку. Само закрытие оборвавшегося SSH-сеанса серверное задание не уничтожает.

Один сервер принимает только одно активное задание BenchForge. Подготовка образа и новый запуск блокируются, пока работает другое задание или остаются его неочищенные контейнеры БД. Завершите получение предыдущего задания, чтобы очистить их.

## Что сохраняется

На сервере задания находятся в `~/.local/share/benchforge/jobs/<ID>`: настройки, журнал `events.jsonl`, ошибки `error.log`, код завершения, папка `reports` и архив отчёта. Отчёт остаётся там после получения; автоматическая очистка удаляет только контейнер агента и его временные контейнеры БД с проверенными метками владельца. Общая очистка Docker не выполняется.

На ПК сохраняются обычные `report.json`, `summary.json`, `results.csv` и файлы ресурсов. Архив проверяется по SHA-256, а настройки и принадлежность измерений — перед загрузкой. В отчёте указаны сервер, CPU, доступная серверу память, ОС, архитектура и образ агента. ОС управляющего ПК записывается отдельно. Локальные пути к SSH-ключам в отчёт не попадают.

Базы по-прежнему запускаются последовательно, с новым экземпляром для каждой комбинации движка, БД, объёма, параллельности и повтора. Этапы одного плана используют общий подготовленный набор данных. Механизм чистой VM — отдельный локальный режим, одновременно с серверным он не включается. Для серверного режима нужен собственный тестовый сервер; арендовать его приложение не пытается.

## Командный режим

Исправьте адрес и пользователя в `configs/remote-server.json`. Дополнительные поля `identityFile` и `knownHostsFile` содержат **локальные** пути управляющего ПК.

```sh
dotnet run --project src/BenchForge.Cli -c Release -- --prepare-server --config configs/remote-server.json
dotnet run --project src/BenchForge.Cli -c Release -- --check --config configs/remote-server.json
dotnet run --project src/BenchForge.Cli -c Release -- --config configs/remote-server.json
dotnet run --project src/BenchForge.Cli -c Release -- --resume-server --config configs/remote-server.json
```

Для запуска вручную без удалённого управления можно перенести исходники на Linux и использовать обычный CLI. В таком случае отчёт нужно самостоятельно скопировать обратно и открыть в Desktop.
